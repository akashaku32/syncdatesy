# Celery Scaling Monitoring Runbook

This runbook explains why worker pods scale and how to verify if `maxReplicaCount: 2` with `--concurrency=3` is enough.

## Capacity Model

- Per pod parallel task slots: `3`
- Maximum pods (KEDA): `2`
- Maximum cluster parallelism: `2 * 3 = 6` concurrent tasks

If average task duration is stable and queue depth remains low, this is usually enough.

## Why Pods Scale Up

`k8s/keda/celery-scaler.yaml` uses multiple triggers:

- Redis queue depth (`listName: default`, `listLength: 3`)
- Active task safety list (`listName: celery:keda:active`, `listLength: 1`)
- CPU utilization (`75%`)
- Memory utilization (`75%`)

KEDA evaluates all triggers and uses the highest recommended replica count.
Even if queue depth is low, CPU or memory pressure can still increase pods.

## Detailed Monitoring Commands

Replace `<ns>` with your namespace.

1) Watch pods and scaling behavior:

```powershell
kubectl get pods -n <ns> -l app=celery-worker -w
```

2) Track KEDA scaler status:

```powershell
kubectl get scaledobject celery-worker-scaler -n <ns> -o yaml
kubectl describe scaledobject celery-worker-scaler -n <ns>
```

3) Inspect HPA generated by KEDA:

```powershell
kubectl get hpa -n <ns>
kubectl describe hpa keda-hpa-celery-worker-scaler -n <ns>
```

4) Check queue backlog in Redis:

```powershell
kubectl exec -n <ns> deploy/redis -- redis-cli LLEN default
kubectl exec -n <ns> deploy/redis -- redis-cli LLEN celery:keda:active
```

5) Verify pod resource pressure:

```powershell
kubectl top pods -n <ns> -l app=celery-worker
```

## Decision Guide (Is 2 replicas enough?)

Keep `maxReplicaCount: 2` when all are true:

- `LLEN default` stays near `0-3` for most intervals
- `celery:keda:active` drains promptly after jobs finish
- CPU and memory usually remain below `75%`
- End-to-end migration/job latency is acceptable

Increase replicas (or reduce task cost) if backlog continuously grows, pod CPU/memory is saturated, or job latency breaches SLA.
