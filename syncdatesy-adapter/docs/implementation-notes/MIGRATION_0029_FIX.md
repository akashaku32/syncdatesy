## Important Notes

### Why RemoveIndex + AddIndex Works

The end result is the same as `RenameIndex`:
1. **RemoveIndex** - Drops the old index from the database
2. **AddIndex** - Creates the new index with the new name

This achieves the same goal as renaming, just in two steps instead of one.

### Performance Impact

- **During migration**: Slightly slower than `RenameIndex` (two operations vs one)
- **After migration**: No performance difference - the final database state is identical
- **Production impact**: Minimal - index operations are fast on most databases

### Future Migrations

To avoid this issue in the future:

1. **Always generate migrations on Django 3.2** (not Django 4.x)
2. **Check migration files** before committing to ensure no Django 4.x-specific operations
3. **Test migrations** on the target Django version before deploying

## Django 3.2 vs 4.x Migration Operations

### Operations NOT available in Django 3.2:
- ❌ `migrations.RenameIndex` (Django 4.0+)
- ❌ `migrations.RenameConstraint` (Django 4.0+)
- ❌ `migrations.AddConstraint` with `violation_error_message` (Django 4.1+)

### Safe operations for Django 3.2:
- ✅ `migrations.AddIndex` / `migrations.RemoveIndex`
- ✅ `migrations.AddField` / `migrations.RemoveField`
- ✅ `migrations.AlterField`
- ✅ `migrations.CreateModel` / `migrations.DeleteModel`
- ✅ `migrations.RenameField` / `migrations.RenameModel`
- ✅ `migrations.AlterUniqueTogether`
- ✅ `migrations.AlterIndexTogether`
